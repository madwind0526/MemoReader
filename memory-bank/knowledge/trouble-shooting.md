# Trouble Shooting

> 발생했던 버그와 해결 방법. 같은 문제를 두 번 겪지 않기 위한 기록.

## 동기화로 들어온 항목의 링크 본문이 수집되지 않음

### 증상

기기가 `url` 없이 텍스트만 push하면 서버가 원문에 링크가 있어도 페이지 본문을 가져오지 않고, 정리가 링크 내용 없이 진행됨 (테스트 `pushed pending item is organized...`에서 `page`가 빈 문자열).

### 원인

`cleanMeta`가 `raw.url`만 정규화하고 원문에서 링크를 찾지 않았음. `create()` 경로에는 `extractFirstUrl`이 있었지만 `upsertFromSync` 경로에는 없었음.

### 해결

`upsertFromSync`에서 `meta.url`이 비어 있으면 `extractFirstUrl(input)`로 채움 (`backend/store.mjs`).

## `node --test test/`가 Node 24에서 MODULE_NOT_FOUND

### 증상

`Error: Cannot find module 'C:\...\test'` — 테스트가 1개로 집계되며 실패.

### 원인

Node 24의 `node --test`는 디렉터리 인자를 모듈 경로로 해석한다.

### 해결

글롭 패턴 사용: `"test": "node --test \"test/*.test.mjs\""` (따옴표를 이스케이프해 셸이 아니라 Node가 글롭을 확장하게 함).

## 대소문자만 바뀐 카테고리로 이동할 때 파일이 사라질 위험

### 원인

Windows/macOS 파일 시스템은 대소문자를 구분하지 않아 `items/A/x.md`와 `items/a/x.md`가 같은 파일인데, "이전 경로 != 새 경로"로 판단해 이전 파일을 지우면 방금 쓴 파일이 삭제된다.

### 해결

`samePath()`로 플랫폼에 맞게 비교한 뒤에만 삭제 (`backend/store.mjs`). 테스트 `items move to their category folder...`가 `DNS → dns` 변경을 포함.

## Node에서 서비스 워커 테스트가 끝나지 않고 멈춤

### 증상

빌드된 `sw.js`를 `vm`에서 실행하는 테스트가 통과 로그 없이 멈추고 `node --test`가 종료되지 않음.

### 원인

워커 코드의 `new BroadcastChannel(...)`을 Node가 열린 핸들로 취급해 이벤트 루프를 붙잡음 (브라우저에서는 문제없음).

### 해결

테스트 샌드박스에 `postMessage`를 기록하고 `close()`가 있는 가짜 `BroadcastChannel`을 주입 (`test/sw.test.mjs`).

## 브라우저 자동화에서 알림 권한/푸시 구독을 검증할 수 없음

`Notification.requestPermission()`이 자동화 Chrome에서 응답 없이 `default`로 남아 실제 `pushManager.subscribe`까지 가지 못함. 그래서 워커 로직은 `test/sw.test.mjs`로, 푸시 전달 자체(FCM 등)는 실기기에서 확인해야 한다.

## `claude` 실행 실패(종료 코드 1)인데 이유가 비어 있음 — 짧은 시간에 40건 실패

### 증상

한 시간대(약 11분)에 40개 메모가 `claude 실행에 실패했습니다 (종료 코드 1):` 뒤에 아무 이유 없이 실패. 직후 같은 호출은 정상(종료 코드 0). 그 사이 사용자가 제공업체를 `codex-cli`로 바꿔 둔 상태였음.

### 원인

- 일시적 실패(원인 확정 못 함 — 사용 한도, 로그인, 네트워크 중 하나로 추정). 시험 중 `claude`를 같은 시각에 따로 호출하기도 했음
- 이유가 안 보인 것은 CLI가 오류 사유를 **표준 출력**에 쓰고 표준 오류는 비워 두는데, 앱이 표준 오류만 메시지에 넣었기 때문

### 해결

- 오류 메시지에 `stderr`가 비어 있으면 `stdout`(정리한 것)을 대신 넣음 (`backend/llm.mjs` `runCommand`, 테스트 `llm.test.mjs`)
- 실패한 것만 다시 정리하는 버튼 추가 (PATTERNS.md "실패한 것만 다시 정리")

## 메모를 많이 저장하면 정리가 한참 밀림 (건당 중앙값 17초, 평균 26초)

### 증상

링크를 7~10초 간격으로 연달아 저장하면 처리(건당 17~26초)가 저장 속도를 못 따라가 "정리 대기"가 수십 건 쌓이고, 가끔 60~170초 걸리는 건이 섞임. 정리는 한 번에 한 건씩만 처리함.

### 원인 (실측)

- 페이지 본문 가져오기는 0.1~1.4초로 병목이 아님
- 시간의 대부분은 `claude -p` 호출 (17~19초). 작은 모델(haiku)로 바꿔도 22.8초로 빨라지지 않음 → 모델 생성 속도가 아니라 CLI를 켤 때 불러오는 MCP 서버·플러그인·훅·스킬·기본 시스템 프롬프트의 고정 비용

### 해결

`claude` 호출에서 불필요한 것을 끔 (옵션과 시험 결과는 PATTERNS.md "CLI LLM 호출"). 같은 입력 18.7초 → 9.1초, 임시 서버에 링크 6개를 한꺼번에 넣었을 때 45.7초(건당 7.6초), 태그 10개 안팎, 느린 건 없음.

### 남은 방법 (아직 안 함)

동시에 2건 처리: 속도는 더 빨라지지만 두 건이 서로의 새 카테고리를 못 봐서 이름이 갈릴 수 있음(이미 `리빙 제품`/`생활용품` 같은 중복 후보가 있음). 쓰려면 카테고리 병합 기능과 함께 도입 권장.

## 푸시 알림은 왔는데 폰이 PC에 연결하지 못함 ("PC에 연결하지 못했어요")

### 증상

앱이 닫힌 폰에 알림이 "메모를 동기화하는 중이에요" → "PC에 연결하지 못했어요. 눌러서 앱을 열면 다시 시도해요"로 바뀜. 서버는 켜져 있었고 앱을 열면 정상 연결됨.

### 원인 (추정, 단정 불가)

푸시로 깨어난 직후 폰의 Tailscale 연결이 아직 살아나지 않아 첫 시도가 실패했을 가능성. 당시 코드는 재시도 3회(0/4/10초), 시도당 4초 제한이었고 실패 원인(`OfflineError`)을 버려서 이유를 알 수 없었음.

### 해결

- 재시도를 0/5/15/30초 4회, 헬스 체크 12초로 늘림 (`src/sw.ts`)
- `OfflineError.detail`에 실제 원인(예: `TypeError`, `TimeoutError`, JSON이 아닌 응답)을 보관하고, 푸시 동기화 실패 시 IndexedDB meta(`lastPushSyncError`)에 남겨 설정 화면에 표시
- 알림 표시 실패(`showNotification` 거부)가 동기화를 막지 않도록 분리하고 `lastPushError`로 기록
- 결과: 개선 배포 후 같은 폰에서 테스트 푸시가 "테스트 알림이에요. 동기화도 확인했어요."로 성공 (2026-10-12)

## 실기기에서 확인된 것 (2026-10-12, Android 폰 + Windows PC)

- Tailscale 경유 HTTPS 접속, PWA 설치, 설정의 알림 켜기(FCM 구독 1건)
- 폰 앱을 완전히 닫은 상태에서 저장한 메모 2개가 PC 재시작(자동 시작 작업 `MemoReader`로 기동) 후 푸시로 올라가 정리되고, 폰에서 결과 확인
- 서버가 푸시를 보낸 시점과 폰이 PC에 올린 시점 사이에 약 40초 지연이 있었음 (일반 우선순위 푸시의 절전 모드 지연 가능성, 미확정)

## 아직 확인하지 못한 것

- 폰 공유 메뉴(Web Share Target)로 다른 앱에서 바로 저장하는 흐름
- iOS Safari는 Web Share Target을 지원하지 않는 것으로 알려져 있음(이 환경에서 확인 불가) — iPhone을 쓴다면 공유 시트 대신 앱 내 붙여넣기/텔레그램 봇 사용
- 텔레그램 봇 실제 수신 (토큰 없이 단위 테스트 범위 밖)
